# T11 — 生态集成与兼容矩阵

## 目标

补上 v1.0.0 最大的证据空白：连接器**从未在任何 Hadoop 生态组件下运行过**
（T06/T07 的验证均为 `FsShell` 等效方式）。按各组件的**真实使用姿势**逐项验证
MapReduce / YARN / Hive / Spark / HBase / Tez / Flink / DistCp，覆盖安全集群与
混合部署形态，产出对外的**《组件支持矩阵》**与四维兼容矩阵结论。

本阶段是全方案工期最长、最可能推翻发布结论的一段。

## 前置依赖

T08 DONE（E3 Hadoop 生态集群 + E4 矩阵镜像可用）；T09 无 S1/S2 未关闭缺陷。
必读：**`docs/TEST-CASES-ECO.md`（本阶段的主用例集）**、`docs/TEST-PLAN.md` §9/§11、
`docs/TEST-CASES.md` COMPAT 节。

## 工作内容

### 0. 前置 spike（**最先执行，3–5 天，可先于 T08**）

执行 TEST-CASES-ECO.md §3 的 `SP-01`–`SP-08`，逐条给出成立/不成立结论：
MR staging 目录属主校验、`access()` 组鉴权、chown 静默失效、
Spark checkpoint 原子创建语义、HBase WAL 可见性、Kerberos 适用性、
DistCp `-update` 校验、YARN 日志聚合目录权限。

**任一条成立即立刻上报**——它可能改变 T11 范围甚至产品路线（需先做一轮产品增强）。
结论写入 `docs/ECO-FINDINGS.md`（体例同 `docs/FAULT-BEHAVIOR.md`：
现象 / 根因 / 复现命令与原文 / 影响面 / 是否需产品增强）。

### 1. 分组件场景执行（TEST-CASES-ECO.md §4，88 条）

- **CLI**（8）：发行版 `bin/hadoop fs` 全命令面、chown/chgrp/chmod、du/count/df、
  getmerge/appendToFile/truncate、setrep、Trash、checksum、HAR；
- **MapReduce**（14）：两种部署形态（`fs.defaultFS=ceph://` 与 HDFS 为主 + ceph 为辅）、
  FileOutputCommitter v1/v2、推测执行、AM 重启恢复、小文件 split、本地性命中率、
  JobHistory 目录、DistributedCache、TeraSort 100GB、**作业运行中 MDS failover**；
- **YARN**（8）：日志聚合（TFile/IFile 两种 controller）、NM 长跑 24h 的 mount 累积、
  public/private 资源本地化、容器以非提交用户读写；
- **Hive**（14）：建库建表、外部表、`INSERT [OVERWRITE]`、动态分区 ≥500、
  1 万分区扫描、`ANALYZE`、`MSCK REPAIR`、`DROP`+Trash、`TRUNCATE`、CTAS、
  scratchdir 权限、ACID 表评估、授权预检、MR/Tez 双引擎；
- **Spark**（10）：Parquet/ORC 批读写、提交协议 v1/v2、**Structured Streaming
  checkpoint**、event log + rolling、并行分区发现、动态分区覆盖、推测执行、
  Spark on YARN cluster 模式、Delta/Iceberg 评估；
- **HBase**（5，评估）、**Tez/Flink**（4，评估）；
- **DistCp**（7）：双向 + `-update` + `-p` + 10 万文件中断重跑；
- **安全与多租户形态**（5）：Kerberized 集群、keyring 分发风险、proxy user、
  双租户隔离、日志无密钥；
- **混合部署与迁移**（5）：双 scheme 共存、跨 FS 作业、分区跨 FS、jar 冲突、混版滚动。

### 2. 兼容矩阵（COMPAT-01–COMPAT-12）

`scripts/env/compat-matrix.sh` 驱动 E4 镜像逐格执行 L2 契约 + 一条端到端冒烟。
**COMPAT-09（libcephfs.jar 与 jni so 版本错配）为 P0 负向用例**——必须早失败且可诊断。

### 3. 结论沉淀

- **《组件支持矩阵》**（README + DEPLOY.md）：每个组件标注

- `docs/COMPAT.md`（四维矩阵，绿/黄/红 + 豁免理由）；
- DEPLOY.md 增补：真实发行版安装与验证（补 T07 遗留 4）、各组件配置示例、
  由 spike 结论产生的"已知限制"条目；
- 附录 A 相关项结论化：A-2（可见性）、A-5（checksum）、A-9（owner/group 用户名映射）、
  A-10（安全集群口径）、A-11（truncate）。

## 验收标准

1. `SP-01`–`SP-08` 八条 spike 全部有明确结论与复现记录；成立项已上报并评估影响面；
2. TEST-CASES-ECO.md §4 的 **P0 场景（20 条）全部通过**；P1 通过或有书面豁免；
   P2 至少有书面结论；
3. **不支持的能力必须"明确失败 + 可读消息"**，抽查确认无静默产生错误数据的情况
   （这是比"支持"更硬的判定）；
4. `fs.defaultFS=ceph://` 与"HDFS 为主 + ceph 为辅"**两种部署形态**的 MR 全链路均跑通；
5. Spark Structured Streaming checkpoint 场景可重启恢复且不重不丢；
6. COMPAT P0 全绿、P1 全绿或豁免，COMPAT-09 表现符合"早失败 + 可诊断"；
7. 《组件支持矩阵》发布，第三方可据其判断自身技术栈可用性；
8. DEPLOY.md 的发行版安装路径经真实 Hadoop 3.3.6 发行版实测。

## 边界与禁止事项

- **不实现产品增强**（owner/group 映射、`getFileChecksum`、`truncate`、Token 等）：
  结论与建议进附录 A，实现另立任务；
- 不做性能调优与长稳（T10/T12）；生态场景的性能数据只作记录，正式基线以 T10 为准；
- 不修改生态组件源码；适配只允许在配置层，且须写入 DEPLOY.md；
- E4 镜像与 E3 集群不得内置真实密钥；Kerberos 场景的 keytab 不入库。
