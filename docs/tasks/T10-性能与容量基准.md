# T10 — 性能与容量基准

## 目标

建立**可复现、可比较、可回归**的性能基线：以同机内核态 CephFS mount 为 100% 参照，
量化连接器在吞吐、元数据 OPS、延迟分位、资源占用上的表现，验证是否达到发布阈值，
并定位实现层的性能敏感点（N+1 元数据 RPC、每次 `hflush` 全量 fsync、
BlockLocation 的 fd 开销等）。

## 前置依赖

T08 DONE（E2 集群 + 指纹归档可用）；T09 建议先完成（避免在有已知 S1/S2 缺陷时测性能）。
必读：`docs/TEST-PLAN.md` §7、§2 性能阈值；`docs/TEST-CASES.md` PERF-* 节。

## 工作内容

1. **对照基线**：同一 E2 集群、同一 pool，用内核 mount + fio 建立顺序/随机、
   1/4/16/64 并发的参照数据；同时记录 `ceph-fuse` 参考值。所有连接器结果以
   **占内核 mount 百分比**呈现。
2. **基准工具** `scripts/bench/`：
   - `io-bench.java`：纯 `FileSystem` API 吞吐/延迟微基准（去 MR 噪声），
     支持文件大小、并发、buffer size、object size、localize_reads 参数矩阵；
   - `meta-bench.java`：create/stat/list/rename/delete OPS（mdtest 口径），
     含 1 万/10 万条目目录场景；
   - `run-matrix.sh`：跑 TEST-PLAN §7.3 矩阵，**每组 3 轮取中位数**，
     自动附带环境指纹，输出 CSV；
   - `hadoop-bench.sh`：TestDFSIO + TeraGen/TeraSort/TeraValidate（需 E3 或单机 MR）。
3. **执行 PERF-01–PERF-15**，并采集资源侧数据：客户端 CPU、JVM heap、
   **native RSS**（NMT/pmap）、GC 日志、必要时 async-profiler 火焰图；
   服务端侧记录 MDS/OSD 延迟与慢请求。
4. **敏感点分析**（TEST-PLAN §7.4）：
   - `listStatus` 的 N+1 次 RPC 在 10 万条目目录下的耗时曲线 vs 内核 `ls -l`；
   - `hflush`/`hsync` = 每次 ceph fsync 的小包高频延迟分布（决定 ECO-13 HBase 结论）；
   - `CephOutputStream` 部分刷盘的 `Arrays.copyOfRange` 分配开销（GC 日志佐证）；
   - `getFileBlockLocations` 每次开关 fd 的开销在大作业 split 阶段的放大效应。
5. **调优建议**：基于 PERF-06/07/08 给出 `ceph.client.buffer.size`、
   `ceph.object.size`、`ceph.localize.reads` 的推荐默认值与适用场景（含数据依据）；
   若建议值与当前默认不同，提出改默认值的建议（**不改代码**）。
6. **回归机制**：`scripts/bench/compare-baseline.sh`（与上一版基线比较，
   退化 > 10% 非零退出），接入夜间流水线的性能冒烟子集。

## 交付物

## 验收标准

1. PERF-01–PERF-15 全部执行，结果表齐全且每项标注 3 轮中位数与波动范围；
2. §2 性能阈值逐条判定：单流 ≥ 70%、8 并发 ≥ 85%、元数据 OPS ≥ 60%、
   元数据 p99 < 100 ms；未达标项均有缺陷单与根因分析（含是否为实现问题）；
3. 每份性能数据都能追溯到环境指纹——**无指纹数据一律作废重跑**；
4. `run-matrix.sh` 可一键复现全矩阵；`compare-baseline.sh` 在人为注入退化时
   能正确判负（自测 1 次）；
5. 敏感点分析 4 项均有量化结论，并对附录 A-3 给出明确"需要/不需要优化"的建议。

## 边界与禁止事项

- **不做性能优化实现**：只产出数据、结论与建议；
- 性能测试期间 E2 集群独占，禁止与故障注入/长稳并跑（会污染数据）；
- 不调整集群侧非默认参数来"美化"数据；若为对比而调参，必须双份记录（默认 + 调优）
  并标注；
- 不改产品默认配置值（建议进文档，改动另立任务）。
