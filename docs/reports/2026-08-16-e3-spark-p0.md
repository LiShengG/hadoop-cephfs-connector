## Findings

Each application lost one initial Parquet task while creating its CephFS mount:

- v1: node-26 executor 3, stage 0 task 2.0, `java.io.IOException: Connection timed out`
- v2: node-44 executor 3, stage 0 task 1.0, `java.io.IOException: Connection timed out`

Spark retried both tasks and the final row, uniqueness, sum, marker, part-file, and residue predicates
all passed. The timeouts remain evidence of unstable mount establishment; they are not hidden by the
final application status.

After cleanup, a read-only `ceph fs status cephfs-e2` command timed out after 20 seconds. The client
session list was therefore not available for a reliable post-run comparison. No session was evicted
or otherwise modified. This observation is consistent with the risk tracked by
[LIM-006](../KNOWN-LIMITATIONS.md#lim-006-native-session-lifecycle).

## Limitations

This run validates the P0 format and commit predicates only. It does not establish retry-free mount
availability, Spark cluster deploy mode, speculation, dynamic partition overwrite, large partition
discovery, or long-running session stability.

## Follow-up

Investigate the mount establishment and post-run MDS responsiveness before treating Spark execution
as reliability evidence. Keep ECO-SPK-01 and ECO-SPK-02 as functional passes and retain the timeout
observations for the SOAK-04/SOAK-05 investigation.
